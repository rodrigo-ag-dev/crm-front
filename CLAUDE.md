# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All commands run from `crm-front/`.

```
npm run dev        # Vite dev server on :5173
npm run build       # tsc -b && vite build
npm run lint         # eslint .
npm run preview      # preview the production build
```

There is no test runner configured (no Jest/Vitest/RTL, no test script) — this project currently has zero automated frontend tests. Don't assume a `npm test` command exists.

## Architecture

```
src/
  pages/          One file per route (Login, Dashboard, Deals, SalesFunnel, TicketFunnel, Companies,
                   Contacts, Tickets, Stages, UserSettings). Each page owns its own data fetching and
                   state — there's no global state manager (no Redux/Zustand), just useState + Context.
  components/     Shared, reusable components (flat, not grouped by feature): Layout, Modal, ConfirmModal,
                   Input, Textarea, DataTablePage (generic table+pagination+toolbar shell used by most
                   list pages), GenericCombobox and its CompanyCombobox/ContactCombobox/StageCombobox
                   specializations, DealModal, ColorPicker, ThemeSelector, LanguageSelector.
  contexts/       AuthContext (session state, backed by GET /api/auth/me — see below), LanguageContext.
  services/       api.ts is the single axios instance (baseURL http://localhost:8080/api,
                   withCredentials: true so the httpOnly auth cookie is sent). Domain-specific services
                   (parameterService, ticketService, ticketStageService) wrap it for specific endpoints;
                   most pages just call `api.get/post/delete` directly instead of going through a service.
  hooks/          useHealthCheck (backend online/offline indicator in the topbar), useFocusFirstInput,
                   useTranslation.
  locales/        pt-BR.json (default), en-US.json, es-ES.json. Hand-rolled i18n (no react-i18next) —
                   useTranslation() does a dotted-path lookup + {param} interpolation. Missing keys log a
                   console.warn and render the raw key.
  utils/          dateUtils/numberUtils (locale-aware formatting), themePreferences (light/dark, persisted
                   to localStorage, applied before React mounts in main.tsx to avoid a flash), 
                   animationPreferences (user-configurable animation toggle, see below).
```

## Auth state

The backend issues an httpOnly session cookie — the frontend never stores a token (not in `localStorage`, not in memory as a readable string). `AuthContext` calls `GET /api/auth/me` once on mount to determine whether a session exists and populate the user object; `ProtectedRoute` in `App.tsx` renders nothing until that check resolves (`isLoading`), then redirects to `/login` if unauthenticated. `signOut()` calls `POST /api/auth/logout` before clearing local state. When adding a new authenticated API call, you don't need to attach anything — `withCredentials: true` on the shared `api` instance handles it.

## Reports (PDF)

`pages/Reports.tsx` (route `/reports`, nav icon `FileText`) — a single page covering all 5 report types (Empresas, Contatos por Empresa, Tickets por Contato e Empresa, Negócios por Empresa, Agenda do Dia) via a type selector plus a filter form that swaps fields per type, reusing `CompanyCombobox`/`ContactCombobox`/`StageCombobox` and native `<input type="date">`/`<select>` (same as everywhere else — no date-picker or select library). No dedicated `reportService.ts` — the page calls `api` directly like most pages do.

"Gerar PDF" calls `api.get('/reports/<type>', { params, responseType: 'blob' })`, builds an object URL, and opens it in a preview `Modal` (`contentClassName` — `Modal.tsx` grew this optional prop specifically so this one modal could be wider/taller than the default 500px) instead of downloading immediately. Only on the actual download/print action does it touch the filesystem:
- **Desktop** (or any browser reporting `navigator.pdfViewerEnabled === true`): an `<iframe src={blobUrl}>` renders the PDF inline, with "Imprimir" (`iframe.contentWindow.print()`) and "Baixar" (`<a download>`) buttons.
- **Mobile fallback (gotcha)**: most mobile browsers have no PDF viewer registered for `<iframe>` content — instead of the PDF, the user sees raw bytes as text with the browser's own generic "open" fallback. `supportsInlinePdf()` in `Reports.tsx` detects this *before* rendering the iframe (via `navigator.pdfViewerEnabled` where available — Chrome/Edge/Firefox — otherwise a mobile-UA regex fallback for Safari/older browsers) and swaps in a `previewUnavailable` message with "Abrir em nova aba" (`window.open(blobUrl)`) and "Baixar" buttons instead. Don't try to reactively detect a broken render (no reliable error event fires for "wrong content type") — the proactive check is the only thing that works here.

`pages/Reports.module.css` holds the page-local layout (filter grid, type-selector row, `.previewModal`/`.previewFrame`/`.previewUnavailable`).

## Tasks / checklists

`services/taskService.ts` wraps `/api/tasks`. Consumption points:

- **`components/TaskWidget.tsx`** — embedded directly in the detail pane of Deals, Contacts, Companies, and Tickets (see the `<TaskWidget entityType="..." entityId={id} />` block near the end of each page's `detailPane`/`RecordPane` children). Shows that record's tasks with a small progress ring, quick-add input, and an expandable checklist per task. Reuses global classes (`card`, `btn-secondary`) plus its own `TaskWidget.module.css`.
  - **Gotcha (fixed, but watch for regressions)**: `RecordPane.module.css`'s `.relatedGrid` (the CSS Grid wrapping the Contatos/Negócios/Tickets `RelatedSection` tiles, immediately above the `TaskWidget` card) used to carry `min-height: 0`. As a *flex item* whose content is itself a multi-row *grid*, `min-height: 0` overrides the browser's automatic minimum size and lets the grid report a height to the flex layout that only covers its first row — the remaining rows still paint (grid `overflow` is `visible`), just outside the box the flex column reserved for them. The next sibling (the `TaskWidget` card) then gets placed right after that too-short box and visually overlaps whatever grid rows spilled past it — worse on narrow/mobile widths where `.relatedGrid` collapses to one column (three stacked rows instead of a 2-3 column layout, so the miscalculation is more visible). Fix: `.relatedGrid` no longer sets `min-height: 0` (uses `flex-shrink: 0` instead, so it can't be squeezed but also can't under-report its height), `.relatedCard` no longer has `max-height: 100%; overflow: hidden` (another source of unpredictable clipping in the same nested flex/grid context), the per-card scroll cap moved to `.relatedList { max-height: 220px }` (a real pixel value, not a percentage resolved against an ambiguous flex/grid parent), and `.pane` scrolls (`overflow-y: auto`) unconditionally instead of only below the 880px breakpoint. If you add another CSS Grid as a flex-column child anywhere in this codebase, don't give it `min-height: 0` unless you're certain every row fits in one viewport — verified via `getBoundingClientRect()` in a browser, not just visually, since the overlap silently disappears when there's little enough content to fit in one row.
- **`pages/MyDay.tsx`** (route `/my-day`, nav icon `CheckSquare`) — **Kanban-only**, no list view: a 3-column board (`PENDING`/`IN_PROGRESS`/`DONE`, i.e. A fazer/Fazendo/Concluído) using the same native HTML5 drag-and-drop as `TicketsKanbanView.tsx` (no DnD library), reusing `Funnel.module.css`. There's deliberately no `ViewToggle`/list mode and no inline quick-add form on this page — task creation happens exclusively through the global capture flow below (`components/QuickAddTask.tsx`) or the per-entity `TaskWidget`. `utils/taskDueBucket.ts` still drives the overdue/today color-coding on each card.
- **`utils/taskEvents.ts`** — a tiny `window.dispatchEvent`/`addEventListener` pub-sub (`emitTaskChanged`/`subscribeTaskChanged`). Tasks can be created or change status from several disconnected places at once (`QuickAddTask`, `TaskWidget`, `NotificationBell`) with no shared state/context between them — each calls `emitTaskChanged()` after a successful mutation, and `MyDay.tsx` subscribes to refetch its board. Without this, e.g. creating a task from the global quick-add bar while looking at the Kanban wouldn't show the new card until a manual reload.

**Fase 2 (implemented)**: `services/notificationService.ts` wraps `/api/notifications`. `components/NotificationBell.tsx` sits in `Layout.tsx`'s topbar next to the search button — the badge is **pushed** over SSE, not polled (see "Real-time notifications" below) — and when a new notification arrives it fires a browser `Notification` (only if permission was already granted; the dropdown shows an inline "enable" banner otherwise, since permission can only be requested from a user gesture). A `TASK`-type item resolves the underlying task directly (`Concluir`/`Adiar 1 dia`, reusing `taskService`); the other four types (added alongside Financial/Ticket/Deal overdue notifications, see "Notifications" below) just navigate. The opt-out preference (`taskNotifyOverdue`, plus its three siblings `financialNotifyOverdue`/`ticketNotifyOverdue`/`dealNotifyOverdue`) need no bespoke settings UI — each is a global `Parameter` seeded server-side (see `crm-api/CLAUDE.md`) and shows up automatically in the existing generic "preferences" screen (`pages/UserPreferences.tsx`), labeled via `settings.<name>` in the locale files.

**Fase 3 (implemented)**:
- **`utils/naturalLanguageDate.ts`** — parses relative dates/times out of free text per locale (pt-BR/en-US/es-ES: "hoje"/"amanhã"/weekday names/"em X dias" plus "15h30"/"15:30"/"3pm"), stripping the matched phrase from the returned title. Locale comes from `useLanguage()` (`LanguageContext`), so the parser switches automatically with the user's language — not hardcoded to Portuguese.
- **`utils/entityMentionSearch.ts`** — fires the same 4 `/search` endpoints `CommandPalette.tsx` already uses (deals/contacts/companies/tickets) to resolve `@mention` candidates.
- **`components/QuickAddTask.tsx`** — single-line capture bar (visually modeled on `CommandPalette.tsx`: `createPortal` + `modal-overlay`), opened via the global `T` keyboard shortcut (ignored while typing in any input/textarea, wired in `Layout.tsx`) or the floating action button (`quickAddStyles.fab`, rendered fixed bottom-right in `Layout.tsx` — this is the *only* way to create an unlinked/global task from the UI now, `MyDay.tsx` has no form of its own). Live-previews the parsed due date as a chip; typing `@query` shows a dropdown of matching Deal/Contact/Company/Ticket records to link (only one entity per task, matching the backend's single `entityType`/`entityId`).

## Financial (accounts payable/receivable)

`pages/Financial.tsx` (route `/financial`, nav icon `Wallet`) — a single page for both Accounts Payable and Accounts Receivable, toggled via an `EXPENSE`/`INCOME` selector-button pair in the `DataTablePage` `titleActions` slot (same tab-button pattern as `UserSettings.tsx`'s settings tabs, not a full `ViewToggle`). The table lists **installments**, not entries — one row per installment, with a status filter (Pending/Overdue/Paid/Canceled — "Overdue" is computed backend-side, not a stored value) and checkbox multi-select for batch payoff.

- `components/FinancialEntryModal.tsx` — the "new entry" form. As the user fills in total amount / installment count / first installment date / recurrence, it calls `POST /financial/entries/preview` on every change (debounced only by React's own effect batching, no explicit debounce) and renders an editable preview table (per-installment date/amount inputs) below the form fields. Submitting sends those edited rows as `installments` in the `POST /financial/entries` body — this is what lets "split into 10x" avoid 10 manual entries: generate once, tweak individual rows only if needed.
- `components/FinancialPaymentModal.tsx` — payoff modal, reused for both single and batch payoff. Branches on `installments.length === 1`: single payoff shows the installment's original amount (read-only) plus editable "Interest/Fine (+)" and "Discount (-)" fields, live-computing "Total to pay" client-side for display, and calls `POST /financial/installments/{id}/pay` with `interestAmount`/`discountAmount` — the backend computes the actual paid total (`amount + interest - discount`), the frontend's total is just a preview. Batch (from the table's multi-select) has no adjustment fields and calls `POST /financial/installments/pay-batch` with the full `installmentIds` list — always pays each at its exact due amount, matching the backend's batch-has-no-adjustments design.
- **Reversing a payment**: a `RotateCcw` icon button appears only on `PAID` rows in `pages/Financial.tsx`, confirmed via `ConfirmModal`, calling `POST /financial/installments/{id}/reverse` — puts the installment back to `Pending` and clears payment/adjustment fields. This is the only way to undo a payoff (no direct edit).
- **Editing / "redoing" a batch entry**: the pencil icon on any non-paid/non-canceled installment row opens `FinancialEntryModal` with an `entryId` prop (edit mode) instead of `create`. On open it fetches `GET /financial/entries/{id}` — the response's `canRegenerate` flag (false if the entry has any paid installment) decides the modal's behavior: if `true`, amount/installment count/first date/recurrence stay editable and resubmitting calls `POST /financial/entries/{id}/regenerate` (deletes and recreates every installment, same preview-then-edit flow as creation); if `false`, those fields are disabled, a notice explains why (must reverse a payment first), the Parcelas tab shows the entry's actual installments read-only (fetched via `GET /financial/installments/search?entryId=...`), and saving only does a plain `PUT` (description/category/company/contact/notes).
- **Modal layout**: `FinancialEntryModal` uses two tabs ("Dados"/"Parcelas", `FinancialEntryModal.module.css`'s `.tabs`, same `selector-button` styling as `UserSettings.tsx`) instead of stacking the installment preview table below a long vertical form — the modal itself is widened (`.wide`, 720px/90vw via `contentClassName`) to fit the table comfortably. This replaced an earlier single-column, all-fields-then-table layout that felt cramped once installment counts grew.
- `pages/FinancialCategories.tsx` — category CRUD (name/type/color via the shared `ColorPicker`), wired as a tab (`financialCategories`) inside `pages/UserSettings.tsx` alongside `stages`, not a top-level route — same reasoning as why Stages lives there instead of its own nav item.
- No dedicated `financialService.ts` — all three pages call `api` directly, consistent with most of the app.
- **Totalizer cards**: `components/MetricCard.tsx`/`.module.css` is a small shared "stat tile" (colored top bar, icon, label, value, optional skeleton while loading, optional `href` link or `onClick`) extracted from `pages/Dashboard.tsx`'s original inline metric cards so it could be reused — `Dashboard.tsx` now renders both its original CRM metrics row and a new "Saúde financeira" row (`GET /financial/summary`) through it. `pages/Financial.tsx` renders 4 of these above the table (`GET /financial/installments/totals?type=...`, refetched whenever the type tab or an installment mutation changes) — Vencido/A vencer/Total em aberto/Pago no mês. The page's `type` (payable/receivable) tab is synced two-way with the `?type=` URL query param (`useSearchParams`, not just a lazy `useState` initializer — a plain lazy initializer wouldn't react to a second navigation to `/financial?type=...` while the page is already mounted) specifically so `Dashboard.tsx`'s "A receber no mês"/"A pagar no mês" cards (`href="/financial?type=INCOME"`/`"?type=EXPENSE"`) land on the matching tab instead of always opening to the default Despesa tab. These are clickable (`onClick` sets the page's `status` filter, `active` highlights the one matching the current filter), doubling as filter shortcuts on top of being totals — the plain status `<select>` still covers `CANCELED`, which has no dedicated card. `MetricCard`'s value text has `min-width: 0` on the card plus `overflow:hidden`/`text-overflow:ellipsis`/`white-space:nowrap` on the value — without both, a long formatted value (e.g. `R$ 12.345,67 (23)`) forces the grid track wider than its `minmax(…, 1fr)` track and overflows the page horizontally instead of wrapping/truncating.
- **Page-fills-viewport layout, no double scrollbar**: `pages/Financial.tsx` wraps the totals cards + `DataTablePage` in `Financial.module.css`'s `.pageRoot` (`display:flex; flex-direction:column; height:100%; min-height:0`), with `.totalsGrid` left at its natural height and `.tableWrapper` given `flex:1; min-height:0`. `DataTablePage`'s own root is `height:100%` internally (see `DataTablePage.module.css`), so it only resolves correctly against a definite, already-shrunk-by-siblings height when its immediate parent participates in this flex+`min-height:0` chain — skipping either the wrapper or `min-height:0` reintroduces the bug this fixed: the outer page (`Layout.module.css`'s `.pageContent`, itself `overflow-y:auto`) scrolling *and* `DataTablePage`'s own `.tableScrollArea` showing a second, redundant scrollbar. Any other page that renders extra content above/around a `DataTablePage` (stat cards, banners, tabs) needs this same wrapping to stay single-scroll.
- **Auto-fitting page size**: `DataTablePage` accepts an optional `scrollAreaRef` prop wired straight to its internal `.tableScrollArea` div (harmless no-op for the many pages that don't pass it). `pages/Financial.tsx` passes a ref there and feeds it into `hooks/useFittedPageSize.ts` (previously only used by `Deals.tsx`'s custom `SplitViewShell` list) to compute how many installment rows fit the available height, using that as the `size` query param instead of a fixed page size — so the "how many rows show" always matches the actual card height rather than being an arbitrary constant that either wastes space or forces an in-card scrollbar. Each real row needs `data-record-row` (the hook's default measurement selector) — the status-filter `<select>`/batch-pay button were moved out of a fake `<tr>` inside the table into `titleActions` specifically so they don't add an unmeasured row that the hook's fit calculation doesn't account for.
- **Phase 2 (not implemented)**: no receipt/photo upload or OCR/LLM-vision auto-fill yet — see `crm-api/CLAUDE.md`'s Financial section for why it's deferred.

## Company lifecycle status

`pages/Companies.tsx` adds a `status` field (`CompanyStatus`: `LEAD`/`PROSPECT`/`CLIENT`/`LOST`/`INACTIVE`, exported from this file since it's the only consumer) — a manual field the user sets, not derived from deals (a won deal can be an upsell to an existing client just as easily as a first conversion). Shown as a colored pill (`Companies.module.css`'s `.statusBadge` + one `.status<Name>` modifier per value, all via `color-mix()` against the existing semantic vars so both themes stay legible) in three places: the list row (`RecordListRow`'s new optional `badge` prop, rendered before `meta`), the detail pane header (`RecordPane`'s new optional `badge` prop, rendered next to the title — both props were added generically since other pages using these shared components might want the same treatment later), and a `SimpleDropdown` status filter in the page header's `toolbar-actions` next to "Criar Empresa" (moved out of the list-pane header — that strip is too narrow for a labeled dropdown alongside the search bar, see the `SimpleDropdown` note below). The create/edit modal also gets a `SimpleDropdown` for the field itself — no native `<select>` anywhere, per this repo's existing dropdown convention. `pages/Reports.tsx`'s Companies report filter follows the same status list, and **replaced** its old `active`/`statusActive`/`statusInactive` boolean filter outright (not additive) since the new status supersedes it — the report request's `status` query param maps straight to the backend's `CompanyReportFilter.Status`.
- `components/SimpleDropdown.tsx`'s trigger text now has a dedicated `combobox-trigger-text` class (`index.css`) with `overflow:hidden; text-overflow:ellipsis; white-space:nowrap; min-width:0` — the trigger `<span>` previously had no truncation styling, so a long option label (or placeholder like "Todos os status") in a narrow dropdown would overflow the box's border instead of eliding cleanly. This is a shared-component fix, so it applies to every other `SimpleDropdown` in the app (e.g. `Financial.tsx`'s status filter), not just Companies.
- The "Localizar" action (`SplitViewShell`'s `notInPageBanner`, shown when a direct link opens a record that isn't in the current page/filter) on `Companies.tsx` clears `statusFilter` before searching by name — otherwise a company whose status differs from the active filter would stay hidden after the search re-ran, since the filter alone was still excluding it.
- **Native `<select>` cleanup**: `pages/Reports.tsx` had four leftover native `<select>` filters (contacts' active/inactive, tickets' stage and canceled, deals' status) predating this repo's dropdown convention — all converted to `SimpleDropdown`, matching the companies status filter added alongside them. `components/TaskModal.tsx`'s priority field was the only other native `<select>` left anywhere in `src/` (checked via a repo-wide grep for `<select` while doing this cleanup) and got the same treatment. If you add a new single-choice field, use `SimpleDropdown`/`GenericCombobox` — don't reach for `<select>`.

## Maintenance windows

Platform admins (`user.platformAdmin`) schedule maintenance downtime windows from a new "Manutenção" tab in `pages/UserSettings.tsx` (alongside the existing "Empresas"/tenants tab, same `isPlatformAdmin` gate) — `pages/MaintenanceWindows.tsx` (CRUD list, modeled directly on `pages/Tenants.tsx`'s table+modal shape) backed by `services/maintenanceWindowService.ts` (`/api/maintenance-windows`). Cancelling a window is a soft "cancel" (`DELETE`, sets `cancelled` server-side), not a hard delete — cancelled rows stay in the list, greyed out, non-clickable.

- **`components/MaintenanceBanner.tsx`** — polls `GET /maintenance-windows/announcement` (public, no auth) every 60s, same `isCheckingRef`-guarded interval pattern as `useHealthCheck`/`NotificationBell`. Rendered in `App.tsx` **above** `<AppRoutes />`, inside `LanguageProvider` but outside `ProtectedRoute`/`Layout` — so it shows on Login/Setup too, not just authenticated pages, since the maintenance window matters most to someone about to hit a possibly-broken login.
- Shows one of two messages (`maintenanceBanner.upcoming`/`.ongoing` in the locale files) depending on whether `now >= startsAt`; whether the window is "ongoing" is computed once per poll cycle inside the effect (not inline during render) specifically to avoid calling `Date.now()` in the render body, which the `react-hooks/purity` eslint rule flags as impure.
- **Layout: fixed footer, not a top banner.** `MaintenanceBanner.module.css`'s `.banner` is `position: fixed; bottom: 0` (`z-index: 100060`, above the mobile rail drawer's `100050` but below `--modal-z-index: 1000000`) so it doesn't push page content down or get clipped by any scroll container. Since it's `fixed`, every `100vh`-rooted layout needs to explicitly reserve its height or the footer visually overlaps the bottom of that content:
  - `MaintenanceBanner.tsx` measures its own rendered height (`ResizeObserver` on a ref) and writes it to a global CSS custom property, `--maintenance-banner-height`, on `document.documentElement` — `0px` when no window is active/on unmount, the real pixel height while one is showing. Declared with a `0px` default in `index.css`'s `:root` so anything reading it before the component mounts still resolves cleanly.
  - Every place in the codebase that sizes itself off `100vh` reads this var: `Layout.module.css`'s `.appContainer` (`height: calc(100vh - var(--maintenance-banner-height, 0px))`) and the mobile rail drawer (`@media max-width: 640px` `.rail`, same calc), plus `Login.module.css`/`Setup.module.css` (`min-height: calc(...)`) and `PublicTicketChat.module.css`'s `.page` (`height: calc(...)`).
  - Everything *inside* `.appContainer` (`.mainContent`/`.pageContent` flex chain, `DataTablePage`'s `height:100%`, `Financial.module.css`'s `.pageRoot` flex+`min-height:0` chain — see the Financial section above) needed **no changes**: they're all relative/flex-sized off `.appContainer`, so shrinking that one root box automatically shrinks everything downstream. Same for `hooks/useFittedPageSize.ts` — it measures the real DOM box via `ResizeObserver`, so when the footer appears/disappears and `.appContainer` actually resizes, the hook recomputes how many rows fit on its own; it needed no code change, only the CSS root fix.
  - If you add a new top-level page/screen outside `Layout` (like `Login`/`Setup`/`PublicTicketChat`) that roots its height off `100vh` directly, it needs the same `calc(100vh - var(--maintenance-banner-height, 0px))` treatment — anything nested inside an existing flex/height:100% chain doesn't.
- No dedicated notification/toast — always visible while a window is active, not dismissible.

## Public ticket share chat

`pages/PublicTicketChat.tsx` (route `/share/:token`) is a standalone, unauthenticated page — a contact opens the link an agent generated and sees/sends only `CONTACT_MESSAGE`/`AGENT_REPLY` ticket comments (never `INTERNAL_NOTE`, never the rest of the CRM). It's mounted in `App.tsx` **outside** `ProtectedRoute`/`Layout`, and checked via `window.location.pathname` *before* the `isLoading` gate so it doesn't wait on the authenticated `/api/auth/me` check that every other route depends on.

- `services/publicTicketService.ts` — a separate `axios` instance (no `withCredentials`, no `Authorization` interceptor) hitting `/api/public/tickets/{token}[/comments]`, deliberately not reusing the shared `api` instance from `services/api.ts` so an agent's own session cookie is never implicated on this page. It does export its own `getApiBaseUrl()` (mirroring `services/api.ts`'s) purely to build the raw stream URL below — `EventSource` can't go through an axios instance.
- `services/ticketShareLinkService.ts` + `components/TicketShareLinkPanel.tsx` — the authenticated side, rendered in `pages/Tickets.tsx`'s detail pane above `TicketTimeline`. Lets an agent generate/copy/revoke the link (`GET/POST/DELETE /api/tickets/{id}/share-link`); generating replaces any existing active link.
- The chat page force-closes the composer once the ticket is closed/canceled. New comments arrive via the SSE stream described below, not polling.

## The shared per-user stream (Server-Sent Events)

`contexts/UserEventsContext.tsx` opens the **one** `EventSource` on `GET /user-events/stream` (built off `getApiBaseUrl()` since `EventSource` can't go through the axios instance) for the whole signed-in session — mounted by `Layout.tsx` wrapping everything below it (`<UserEventsProvider>...<Outlet /></UserEventsProvider>`), so it only ever opens for an authenticated route. Any feature needing live push subscribes by event name via `useUserEvent<T>(eventName, handler)` instead of opening its own connection — one native `addEventListener` is attached per distinct event name the first time something subscribes to it (`boundEventsRef`), however many components subscribe to that same name. This replaced two features that used to each open their own stream (notifications, then chat) — without the shared context, every additional per-user feature would cost the browser another of its ~6-connections-per-host, on top of whatever ticket comment stream (below) happens to also be open.

`components/NotificationBell.tsx` (`useUserEvent<NotificationStreamEvent>('notification', ...)`) and `components/ChatTopbarButton.tsx`/`pages/Chat.tsx` (`'chat'`/`'chat-read'`) are the two current subscribers — see their sections below. `hooks/useEventStream.ts` still exists as the *per-resource* (not per-user) version backing the ticket comment streams, which are keyed by `ticketId`, not by the signed-in user, so they don't belong on this shared connection.

### Notifications

The bell badge updates the instant the backend creates a notification instead of up to a poll interval later. The old 30s `unread-count` poll is gone; a 60s poll survives only as a fallback for a silently stalled connection. Covers 5 sources now, not just Tasks — see `crm-api/CLAUDE.md`'s "Overdue/due-soon notifications" for the backend side.

- The `notification` event payload carries `unreadCount` — **assign it, never increment a local badge**. It's authoritative server-side (see `crm-api/CLAUDE.md`), so a dropped or duplicated event can't make the count drift. `notification` (an `AppNotification`, `services/notificationService.ts` — generalized from the original task-only `TaskNotification` shape: `entityType`/`entityId`/`title`/`dueAt`/`kind` instead of `taskId`/`taskTitle`/`taskDueAt`) is only present when a genuinely new one arrived; that's what gates the browser `Notification` push, and it supplies the item's own title as its body instead of the generic "you have N new alerts" the fallback poll still uses.
- **`components/NotificationBell.tsx` branches per `entityType`**: `TASK` keeps the original quick actions ("Concluir"/"Adiar", calling `taskService` directly and marking read in parallel); the four newer types (`FINANCIAL_INSTALLMENT`/`TICKET`/`DEAL_CLOSE_DATE`/`DEAL_STAGE_SLA`) render as a plain clickable row (`routeForNotification`) that marks read and navigates — `/financial` (no per-installment detail route exists, so this just opens the list), `/tickets/{entityId}`, or `/deals/{entityId}`. Each non-task row also shows a small category label (`notifications.entityTypeLabel.*`) since the title alone doesn't say which module it's from.
- **`kind` drives the meta line's text and color**: `OVERDUE` reuses the original `notifications.overdueSince` (red); `UPCOMING` (new — the three added sources notify up to 1 day before the deadline too, Tasks still don't) uses `notifications.dueSoon` (`.itemMetaUpcoming`, a warning tone instead of danger).
- Mark-read/mark-all-read also come back over the stream (count-only events), so clearing the bell in one tab clears it in the others.
- The backend only purges stale notifications *lazily, on read*, so nothing gets pushed when the underlying item is resolved elsewhere in the app. The bell covers the **Task** case by subscribing to `utils/taskEvents.ts`'s `subscribeTaskChanged` (which `MyDay`/`TaskWidget`/`QuickAddTask` already emit) and re-reading the count — that read is what triggers the purge. **Known gap**: there's no equivalent invalidation event yet for paying a Financial installment, closing a Ticket, or changing a Deal's stage/close-date from their own pages — those only catch up via the 60s fallback poll (or immediately, if the mutation happens to be the same click that opened the notification and navigated there). Don't replace `subscribeTaskChanged` with a server push from `TaskService`: `PublishUnreadCountAsync` must never fire on a plain read, or a tab reacting by re-reading would loop — the same rule would apply to any Financial/Ticket/Deal equivalent added later.

### Direct chat

`services/chatService.ts` wraps `/api/chat`. `pages/Chat.tsx` (route `/chat`, nav icon `MessageCircle`) is a `SplitViewShell` — conversation list (`RecordListRow`, unread count in its `badge` prop) on the left, the open thread on the right, bubbles styled like `components/TicketTimeline.module.css`'s but in `Chat.module.css` (`.bubbleMine`/`.bubbleTheirs`). Starting a new conversation opens a `Modal` listing `GET /chat/contacts` (debounced search), reusing the same list-row shape rather than a combobox since a person also needs their tenant shown when they're cross-tenant.

- **`components/ChatTopbarButton.tsx`** sits next to `NotificationBell` in `Layout.tsx`'s topbar — badge only, no dropdown (deliberately: reading a chat message means opening the conversation, so there's nothing a popover could show that the `/chat` page doesn't already show better). Reuses `NotificationBell.module.css` so the two icons look identical.
- **Dedupe by message `id`, same race as ticket comments**: the backend publishes the `chat` event before the `POST /conversations/{id}/messages` response returns, so the SSE echo of a message this tab just sent can beat that response back. `Chat.tsx`'s `chat` handler and its own optimistic append after `POST` resolves both check `prev.some(m => m.id === ...)` before appending — skip either side and your own message duplicates.
- **`totalUnreadCount` in the `chat`/`chat-read` payloads is authoritative** across every conversation, same rule as the notification badge — `ChatTopbarButton` assigns it, never increments.
- A conversation is marked read (`PATCH /conversations/{id}/read`) the moment `Chat.tsx` opens it (its `useEffect` on `id`), which is also how a `chat-read` event reaches this same user's *other* open tabs to zero their badge too.
- Cross-tenant conversations (`participant.crossTenant`) show a small tenant-name pill (`.tenantTag`) in the thread header and next to the contact in the "new conversation" list — the entire point of the platform-admin channel is knowing which company you're talking to, since nothing else in the UI would tell you.
- **Reply on behalf of the other participant (impersonation, always audited, automatic)**: `Chat.tsx`'s `isImpersonatingContext` is true whenever `user.platformAdmin`, `user.tenantId !== user.homeTenantId` (a real switch is in effect — see below), and `active.participant.tenantId === user.tenantId` — i.e. the admin has switched (`TenantSwitcher`) into the exact tenant the other participant belongs to, mirroring the backend's own check (see `crm-api/CLAUDE.md`'s "Direct chat"). There is **no manual toggle** — this was tried first and dropped: while that context holds, every send in *this* conversation is automatically routed through `chatService.sendImpersonatedMessage` instead of `sendMessage` (switched right back the moment the admin isn't viewing that tenant, since it's derived from live state, not a per-message choice). A standing notice bar above the composer makes this unmissable while it's in effect. Any message with `impersonatedByUserId` set renders a small permanent `enviado por {name}` tag under the bubble — this can never be suppressed client-side, since the backend DTO always returns it and the whole point of the feature is that it's never indistinguishable from a message the participant actually wrote themselves.
  - **Bug fixed**: the original check only compared `active.participant.tenantId === user.tenantId`, which is trivially true for any colleague in the admin's *own* default tenant even with no switch at all (`user.tenantId` reflects the effective tenant, which equals the admin's home tenant absent an override) — so a completely ordinary same-tenant chat was silently treated as impersonation. `AuthContext`'s `User`/`RawUserPayload` grew `homeTenantId` (from `UserDto.HomeTenantId`, see `crm-api/CLAUDE.md`) specifically to tell "I'm just viewing my own tenant" apart from "I switched into someone else's" — `tenantId` alone can't, since it's the same field either way once effective tenant equals home tenant.
  - **Follow-up gotcha (same bug reappeared)**: the first fix compared `user.tenantId !== user.homeTenantId` directly — but an `undefined` `homeTenantId` (any session whose `user` object was fetched, or cached by Fast Refresh across an edit, before this field existed on the backend) makes that comparison `true` for *any* `tenantId`, which is worse than the original bug: it made impersonation fire for every same-tenant chat unconditionally instead of only when actually mismatched. Fixed by requiring `user.homeTenantId` to be truthy before comparing it at all (`user.homeTenantId && user.tenantId !== user.homeTenantId`) — an unknown/missing value must default to "not a switch", never to "assume switched". A stale cached session still needs a real re-fetch of `/auth/me` (reload or re-login) to pick up the field at all; this only stops the missing-field case from actively lying in the meantime.

## Real-time ticket comments (Server-Sent Events)

`hooks/useEventStream.ts` is the generic subscription (open an `EventSource`, parse each named event, keep callbacks in refs so only the URL drives resubscription, run a long fallback poll). `hooks/useTicketCommentsStream.ts` is now a thin wrapper over it (`eventName: 'comment'`) backing both `components/TicketTimeline.tsx` (agent view) and `pages/PublicTicketChat.tsx` (public share-link view) — each previously ran its own raw `setInterval(..., 5000)` poll, not even sharing a hook, hammering the backend every 5s regardless of activity. Both now open an `EventSource(url, { withCredentials: true })` against the matching backend stream endpoint (`GET /tickets/{id}/comments/stream` or `GET /public/tickets/{token}/comments/stream` — see `crm-api/CLAUDE.md`'s "Real-time ticket comments" section for the server side) and get pushed a `comment` event per new message instead of re-fetching the whole list. `withCredentials: true` is what makes this work with zero extra plumbing — it sends the existing `crm_token` cookie exactly like a normal `axios` request would, since `EventSource` can't set custom headers at all (which is also why this couldn't just reuse the WebSocket/JWT-in-query-string pattern other apps use).

- Both callers de-duplicate by comment `id` in their `onComment` handler (replace-if-present, append otherwise) **and** in the composer's own optimistic append after `POST` resolves (`prev.some(c => c.id === response.data.id) ? prev : [...prev, response.data]`, not a bare append) — necessary because the backend publishes to the broadcaster *before* the `POST` response is even returned (see `crm-api/CLAUDE.md`), so the SSE echo of a just-sent comment can genuinely beat that same request's own HTTP response back to the browser. Whichever of the two lands first wins normally; skipping the dedupe on either side reliably produced a visible duplicate bubble for your own message.
- A `fallbackPoll` still runs, but only every 60s (`fallbackIntervalMs`, configurable) as a safety net for a silently-stalled connection (backgrounded tab, a proxy that drops the connection without firing `EventSource.onerror`) — not the primary delivery path anymore. `EventSource` already auto-reconnects on its own after a transient drop; `onerror` is deliberately a no-op.
- `PublicTicketChat.tsx` also handles a `revoked` event (server-pushed when an agent revokes the share link, or it expires, while the contact still has the page open) by calling `setNotFound(true)` — reusing the existing "link no longer valid" screen rather than a new one. The hook itself calls `EventSource.close()` before invoking `onRevoked`, since the default auto-reconnect behavior would otherwise keep retrying the now-invalid token forever.

## Sidebar: grouping and expand/collapse

`components/Layout.tsx`'s rail (`RAIL_GROUPS`) can expand from icon-only (64px) to icon+label (216px), persisted via `utils/sidebarPreferences.ts` (`localStorage`, key `@CRM:sidebar_expanded`, default `true`) — a lazy `useState` initializer reads it on mount, same pattern as `themePreferences.ts`. Every `RailLink` always renders its label `<span>` in the DOM (`.railLabel`); the `.railExpanded` class on `<aside>` controls visibility/width via CSS (`opacity`/`max-width`) rather than conditional mounting, so the label fades in instead of popping in abruptly, and the hover tooltip (`.railTooltip`, otherwise shown only when collapsed) is hidden outright once expanded since the label already says the same thing.

- **Grouping**: nav items are organized by how they're actually used together, not by data model — `navigation.groupWork` (Meu dia, Chat — daily personal tools), `navigation.groupSales` (Negócios, Empresas, Contatos — the pipeline and the records it feeds), `navigation.groupSupport` (Tickets), `navigation.groupManagement` (Financeiro, Relatórios). Dashboard stays outside every group, as the one fixed entry point. Each `RAIL_GROUPS` entry renders as a `.railGroup` div (its own `.railDivider` + `.railGroupLabel`, the latter collapsing the same opacity/max-height way `.railLabel` does — see the `!important` gotcha below) followed by its `RailLink`s. This replaced a flat `RAIL_ITEMS` list whose order (Financeiro sitting between Negócios and Tickets, Chat off on its own away from Tickets) had no discernible grouping logic. Three unused locale keys from an earlier, different 3-group attempt (`groupCommercial`/`groupCrm`, plus a `groupSupport` that meant something else) were replaced outright rather than added alongside — check `navigation.*` in the locale files before reusing a `group*` key name if extending this further.
- **Expand/collapse control**: a small circular button (`.railEdgeToggle`, `ChevronLeft`/`ChevronRight`) sits right next to the brand logo in `.railBrandRow` (a flex row wrapping `.railBrand` + the toggle — `justify-content: center` collapsed, `space-between` once expanded), instead of the old full-width "Retrair menu" row pinned to the rail's bottom — that row read as a stray nav item and ate a full label's worth of vertical space for a control that isn't navigation. It went through a floating-pill-on-the-rail-edge version first (absolutely positioned, half off the border) before landing here; as a normal flex sibling it needs no absolute positioning or expanded-state CSS variant of its own, since `.railBrandRow`'s `justify-content` swap does the repositioning — only the chevron direction and `aria-label`/`title` (`navigation.expandMenu`/`collapseMenu`) change, driven straight off `railExpanded` in the JSX. `.railBrand` itself shrank (34px → 28px square, icon 18px → 15px) to leave room for the toggle beside it at 64px collapsed width. Hidden outright below the 640px breakpoint (`.railEdgeToggle { display: none }` inside the existing mobile `@media` block) since the off-canvas drawer there is either fully open or fully closed via the topbar hamburger — there's no separate width state to toggle.

**Gotcha (non-obvious, cost real debugging time): a global `!important` rule breaks non-color transitions app-wide.** `index.css`'s "THEME TRANSITION" section has `body, body * { transition-property: background-color, color, border-color, background, box-shadow, fill, stroke !important; ... }`, added so every element gets a smooth light/dark theme switch without opting in individually. Because it's `!important` and matches every element, it silently *replaces* the `transition-property` of any other rule that doesn't also use `!important` — so a plain `transition: width 0.25s` on `.rail`/`.railItem`/etc. compiles fine and *looks* correct in the source, but the browser never actually animates `width`/`padding`/`opacity`/`max-width`/`transform` anywhere in the app; the element just snaps. This is why the mobile drawer's `transform` slide-in (pre-existing, unrelated to the sidebar-expand feature) and the new expand/collapse width transition both needed their own `!important` overrides restating the *full* desired property list (transition shorthand doesn't merge across rules — whichever declaration wins, by importance then specificity/order, replaces the entire list, it doesn't add to it). If you add a new transition anywhere in this app for a property outside that fixed color/shadow list (width, height, transform, opacity, max-width/max-height, flex-basis, ...), it needs `!important` too, or it will silently no-op instead of erroring — there's nothing that flags this at build time.

## Tenant badge

`components/Layout.tsx`'s topbar shows the current tenant name (`user.tenantName`, already returned by `GET /auth/me` via `Data/Users/UserDtos.cs`'s `TenantName`) as an always-visible pill (`.tenantBadge`, `Building2` icon) between the breadcrumb and the search button — not just inside the account dropdown (which already showed it, but only after a click). On narrow screens (`@media max-width: 640px`, same breakpoint the search/account buttons already collapse at) the label text hides and only the icon remains, consistent with the other topbar controls.

- **Platform admins get a clickable tenant switcher instead of the plain pill**: `Layout.tsx` renders `components/TenantSwitcher.tsx` in place of the static badge when `user.platformAdmin` is true (regular users still get the non-interactive div). It reuses the same `.tenantBadge` styling as its trigger button plus the global `.combobox-*` classes (`combobox-wrapper`/`combobox-dropdown`/`combobox-option`) for the dropdown panel, so it looks like every other combobox in the app rather than a bespoke widget. Tenants are fetched once per mount (on first open, via `tenantService.listTenants()` — the same endpoint `pages/Tenants.tsx`'s CRUD list already used) and filtered client-side by a small search input inside the panel; there's no dedicated paginated endpoint for this since the tenant count is expected to stay small enough for one unpaged fetch.
- Selecting a tenant calls `tenantService.switchTenant(tenantId)` → `POST /api/auth/switch-tenant` (see `crm-api/CLAUDE.md`'s "Platform admin tenant switching") which reissues the `crm_token` cookie and returns a fresh user object — the component writes the returned token to `localStorage['crm_token']` (same as `Login.tsx`) and calls `AuthContext`'s `updateUser(...)` to swap `user.tenantId`/`tenantName` in place, **no full page reload or re-login**. It then navigates to `/` (Dashboard) — deliberately not staying on the current route, since a record id in the URL (e.g. `/companies/:id`) has no guarantee of existing in the newly-selected tenant's schema.
- This only changes which tenant's business data (Companies/Contacts/Deals/Tickets/Financial/...) the admin is browsing — it's not a role change and doesn't affect anything scoped by the admin's real identity (their own chat contacts, their own user-management visibility across tenants, etc.), which is why the backend deliberately keeps those on the admin's actual home tenant. See the backend doc section for the exact boundary.

## Clipboard copy (secure-context gotcha)

`utils/clipboard.ts`'s `copyToClipboard(text)` backs both `TicketShareLinkPanel.tsx` (copy the public share link) and `Users.tsx` (copy a reset temporary password). `navigator.clipboard` only exists in secure contexts (HTTPS, or `http://localhost`) — accessing the app over a plain-HTTP LAN IP throws a synchronous `TypeError` on `navigator.clipboard.writeText(...)` (`navigator.clipboard` itself is `undefined`), which silently aborted the whole click handler before either call site had any try/catch. `copyToClipboard` checks `window.isSecureContext` first and falls back to the legacy `document.execCommand('copy')` (via a hidden, off-screen `<textarea>`) when the Clipboard API isn't available or its promise rejects. Returns a `boolean` so callers can show an error instead of assuming success — `TicketShareLinkPanel.tsx` does its own thing; `Users.tsx`'s copy button uses the global toast (see below) to report success/failure.

## Login form errors

`pages/Login.tsx`'s auth-failure message used to be a `<div>` in normal flow above the form — since `Login.module.css`'s `.loginScreen` vertically centers the card (`align-items: center`), that div growing the card's height also re-centered the whole card, reading as a layout "jump" on every failed login. Fixed by making the error a `position: absolute` tooltip (`.errorTooltip`, `Login.module.css`) anchored under the password field instead of participating in the form's normal flow — both fields also get a `.fieldError :global(.input-field)` red border via a wrapper div, since `components/Input.tsx` has no `error` prop and wasn't touched (kept the blast radius to this one page). `.loginSubmit`'s `margin-top` was bumped from 16px to 52px — enough for `login.authError` to wrap onto two lines at the card's 320px content width without the tooltip overlapping the button — a fixed, always-present gap, so there's still no size change between the error/no-error states.
- The tooltip auto-dismisses after `ERROR_DISMISS_MS` (6s, a plain `useEffect`+`setTimeout` keyed on `error`) and is also cleared immediately the moment the user edits either field — it used to only clear at the start of the *next* submit, so a failed login's message sat there indefinitely (covering/overlapping the button before the spacing fix above) until the user tried submitting again.

## Toasts

`contexts/ToastContext.tsx` — the app's first (and only) transient-notification primitive, added specifically because several actions had no success/error feedback at all (the clipboard gotcha above was the concrete case that prompted it). `ToastProvider` wraps the app in `App.tsx` (inside `LanguageProvider`, outside the router-agnostic `AppRoutes`) and renders a fixed bottom-right stack (`ToastContext.module.css`'s `.toastStack`, `z-index: calc(var(--modal-z-index, 1000000) + 100)` so a toast triggered by an action *inside* an open `Modal` — e.g. the copy button in `Users.tsx`'s reset-password result modal — still shows above it). `useToast().showToast(message, type?)` (`type` is `'success' | 'error'`, defaults to `'success'`) queues a toast that auto-dismisses after 4s or on manual close; there's no dedup/queue-cap, since nothing in the app fires toasts in a tight loop today. Messages are passed in already translated (the hook itself has no i18n dependency) — callers use `t('...')` before calling `showToast`.
- Only wired up at `Users.tsx`'s reset-password copy button so far. If you add a new action that needs transient success/error feedback (not a validation error tied to a specific field, not something that belongs in a persistent banner), reuse this instead of inventing another inline `error`/`setError` state — that pattern still exists in older pages (`Chat.tsx`, etc.) but isn't the one to copy going forward.

## Design system

Everything routes through CSS custom properties defined once in `src/index.css` under `:root` (light) and `:root[data-theme='dark']` (dark) — colors, spacing radii, shadows. `main.tsx` applies the stored theme preference (`utils/themePreferences.ts`) before the first render. There is no Tailwind/MUI/component library: styling is plain CSS, split between:
- `src/index.css` — design tokens + global utility classes shared across pages (`.btn-primary`, `.card`, `.data-table`, `.modal-*`, `.form-*`, `.funnel-*`, `.selector-*`, `.combobox-*`, etc.). These are relied on from many pages via plain `className="btn-primary"` strings, not CSS Modules.
- `src/animations.css` — all `@keyframes` plus a couple of motion utility classes. Also defines `.animations-disabled` (toggled on `<body>` by `utils/animationPreferences.ts` from a user setting stored as a backend `Parameter`) and a `prefers-reduced-motion` block.
- Per-component/page `*.module.css` — CSS Modules for anything not part of the shared vocabulary above.

When touching shared visual behavior, check both `index.css` (global classes) and the relevant `*.module.css` — component-local CSS Modules can define a same-named local class (e.g. `DataTablePage.module.css`'s `.pageHeader`) that silently shadows a global one of the same name; they don't inherit from each other.

Mobile layout: the sidebar in `Layout.tsx`/`Layout.module.css` collapses into a slide-in drawer below 880px width (see the `sidebarOpen` state and the `@media (max-width: 880px)` block at the bottom of `Layout.module.css`).
